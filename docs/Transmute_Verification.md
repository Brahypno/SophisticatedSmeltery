# 嬗变炉配方与产物核对（2026-10-25）

验证版本为本地 Maven 发布包 `org.brahypno:esotericism_tinker:1.6.2fix`，运行参数 `-PwithEstinker=true`。可选依赖保持 `mandatory=false`，未安装时不加载嬗变炉绑定配方。

## 合成

- 空白熔炼升级由 8 个 `tconstruct:seared_brick` 围住 `sophisticatedbackpacks:upgrade_base` 合成。
- 空白熔炼升级或可换绑的旧熔炼升级，加 `esotericism_tinker:transmute_controller`，无序合成 1 个嬗变炉升级；同一个升级物品通过控制器 NBT 区分炉型。
- 换绑返还旧控制器，保留新旧控制器各自的 NBT；新升级不继承旧炉运行内容。合成前须排空炉内熔液，内部物品返还沿用共用合成路径。
- 已验证加载的嬗变炉配方在 2×2/3×3 网格中的绑定与换绑、配方展示结果、控制器 NBT、旧控制器剩余物和客户端配方序列化。共用完整物品返还路径另由 `UpgradeGameTests` 覆盖。

## 默认熔炼与副产物

便携层使用真实 `TransmuteBlockEntity` 和 `SuperByproductMeltingModuleInventory`。每槽每批最多 2 个输入，不直接消耗背包整叠；末尾剩 1 个可单独加工，使用默认嬗变模式。

设本批原配方主产物总量为 M、全部副产物总量为 B。这两个量已包含原生矿物倍率与本批数量：

- B 为 0：保留原主产物 M。
- B 大于 0：主产物流体的数量改为 B；副产物流体合计数量改为 M。
- 多种副产物按各自占 B 的比例分配 M，整数除法的余量补给原数量最大的副产物。
- 主产物倍率来自原生 Foundry ore rate，矿物副产物倍率由配方的原生 `handleByproducts()` 决定，便携层没有额外乘倍。

确定数量的测试样例（单位 mB）：

| 原单个配方 | 加工数量 | 默认嬗变模式实际结果 |
| --- | ---: | --- |
| 铁 90；副产铜 30、金 20 | 1 | 铁 50、铜 54、金 36 |
| 铁 90；副产铜 30、金 20 | 2 | 铁 100、铜 108、金 72 |
| 铁 91；副产铜 2、金 3 | 1 | 铁 5、铜 36、金 55 |
| 铁 91；副产铜 2、金 3 | 2 | 铁 10、铜 72、金 110 |

另对实际铁锭、粗铁、粗铜、粗金配方分别执行 1/2 个批次，与独立创建的原生嬗变炉实际熔炼模块逐种流体、逐个数量对照。普通容量下结果一致，输入扣除也与批次一致。当前测试配置下每个输入的结果为：

| 输入 | 实际流体产物（mB） |
| --- | --- |
| 铁锭 | 铁 90 |
| 粗铁 | 铁 30、钢 90 |
| 粗铜 | 铜 10、金 90 |
| 粗金 | 金 30、钴 90 |

双个批次的上述数量均恰好翻倍。配方包或倍率配置变化时仍以实际原生配方结果为准；测试日志的 `ESTINKER OUTPUT` 记录实际流体 ID 和 mB 数量。

## 已确认的原生容量行为

`1.6.2fix` 的 `SuperByproductMeltingModuleInventory.tryFillFluidTransmute()` 仅模拟原主产物 M 能否装入；之后实际依次写入交换后的所有主副产物，未检查这些 `fill()` 的完整接收量。因此：

- 炉满或剩余空间小于 M 时暂停且不扣输入。
- 剩余空间达到 M、但不足 M+B 时，仍完成加工并扣除整批输入，超出容量的产物丢失。
- 样例“铁 90、副产铜 30、金 20”加工 2 个，应产生 280 mB；只剩 180 mB 空间时实际产出 180 mB，丢失 100 mB，两个输入均被扣除。
- 样例“铁 91、副产铜 2、金 3”加工 2 个，应产生 192 mB；只剩 182 mB 空间时丢失 10 mB。

两个场景在原生模块和便携层都已复现。用户确认这说明正确调用了嬗变炉提供的熔炼模块，本轮以保持原生行为为验收标准。因此合成、正常产出和容量边界对照均通过，容量截断作为已知原生行为保留。本次核对没有改写 estinker 的产物算法或修改其项目源码。

## 九格槽中的加热器与加速器

用户指定将加热器、加速器放在原有九格方块槽内生效。已接入原生 `transmute_heater`、`transmute_accelerator` 方块判定，按各槽物品数量累计，同时作为原生标签允许的结构材料参与容量计算。

- 加热器温度与加速器速率继续由 estinker 的配置和实际 `heat()` 方法计算。默认每个加热器提供 500 度，原生额外速率为总加热温度 / 100；每个加速器额外提供 15 加热速率。
- 有效温度由燃料温度加上加热器温度组成；选择最低够用燃料时先扣除加热器贡献。
- 原生结构和储罐要求仍然适用；有足够加热器及空燃料罐时，可以不消耗燃料加热。加速器本身不提供温度。
- 放入、取出、同数量替换立即刷新效果；容量改变及配方/标签重载后重算。保存的是原九格物品，恢复时重建效果，不额外保存另一份组件数量。
- 仍遵守总加热开关；热量条的温度判断包含加热器贡献。计数只在组件或结构改变时更新，不在每 Tick 遍历九格。

服务端测试通过实际背包升级验证槽位接收、堆叠数量、同数量替换、原生加热速率、移除、总开关、重载，以及加热器加岩浆达到目标温度时不消耗更热燃料。

## 验证范围

规则及组件对照由 `EstinkerBaselineGameTests` 的 4 个测试入口覆盖，运行 `gradlew.bat runGameTestServer build -PwithEstinker=true --offline`。具体运行日志与完整回归数量见 [Implementation_Status.md](Implementation_Status.md)。

模式方块、外接合金开关尚未映射到背包；当前升级不能在 GUI 切换到冶炼炉/熔铸炉/第四模式。本次对照使用实际原生控制器及模块，没有搭建世界中的完整多方块结构，也不替代长期存档验收。

## 捕获生物熔炼

物品与生物熔炼统一覆盖已支持的炉型，生物路径不再另设控制器白名单。嬗变炉及其子类通过可选适配器使用实际 estinker 配方缓存：

- 先查询 `ByproductEntityMeltingRecipeCache`，保留原生优先级和配方 ID 的同优先级选择规则。使用配方给出的伤害、主产物和全部副产物，不套用物品嬗变的数量交换算法，也不额外应用回退倍率。
- 没有专用配方时，回退到匠魂生物配方；无配方时使用嬗变炉原生默认液态灵魂。按 estinker 的 `BYPRODUCT_ENTITY_MELTING_MULTIPLIER` 配置放大流体，默认 2 倍。
- 九格中的加热器可提供生物熔炼所需热源，不必消耗液体燃料；没有加热器时仍需实际燃料。
- 延用总加热开关、前 X 格占位范围、黑名单和免疫、真实伤害/死亡/掉落、生命值写回、满包掉落队列及保存同步。
- 遵守已确认的捕获生物保护规则：主产物加全部副产物合计放不下时，暂停且不伤害生物、不点燃燃料。这个捕获生物规则与上文物品熔炼沿用的原生产物截断是两条既有边界。

可选模组的类只在已加载 estinker 的分支使用。原生对照使用独立的 `ByproductEntityMeltingModule`；背包路径直接调用原生配方/缓存 API，伤害和掉落由共用便携流程处理，没有在世界中放出捕获生物进行扫描。

有/无 estinker 的生物回归、构建和实际嬗变炉生物熔炼/磁盘重进客户端验证均已通过，详见 [Implementation_Status.md](Implementation_Status.md)。缺失控制器现在回退为空白停用状态，保留原始 NBT，允许取下；不接受新物品、不加工或传输炉液，也不会将空状态覆盖回原内容。包含该回退的完整测试为 36 项；此前卸载 estinker 后崩溃的旧测试存档也已实际重开并通过回归。
